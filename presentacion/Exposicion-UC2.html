01 / FUNDAMENTO · A01:2021

Broken Access Control

Fallo al aplicar los permisos de un usuario.

Autenticación: ¿quién eres?

Autorización: ¿qué puedes hacer?

Impacto: leer, modificar o borrar datos ajenos.

EJEMPLO: IDOR

Ana inicia sesión correctamente.

GET /notas/1 → nota de Ana

Cambia el identificador:

GET /notas/2 → nota de Bruno

El ID selecciona el objeto; no concede permiso.

OWASP A01:2021 · Validar permisos por objeto y por operación en el servidor.

01 / MITIGACIÓN INMEDIATA

Autorizar antes de devolver el objeto

La identidad viene de la sesión del servidor.

Comprobar el propietario de cada nota.

Ana + nota 1 → HTTP 200.

Ana + nota 2 → HTTP 403.

mitigado/app.js · obtenerNota (fragmento)

if (nota.propietario !== usuario) {
  return {
    estado: 403,
    error: 'Acceso denegado: esta nota '
      + 'pertenece a otro usuario.'
  };
}

return { estado: 200, nota };
Ocultar botones o usar UUID no sustituye la autorización en backend.

02 / FUNDAMENTO · A03:2021

XSS: datos que el navegador ejecuta

Entrada no confiable se interpreta como HTML ejecutable.

Tipos: reflejado, almacenado y basado en DOM.

Nuestra demo: XSS reflejado.

Impacto: alterar la página o actuar con la sesión de la víctima.

DEL DATO AL CÓDIGO

Usuario envía un comentario.

El servidor lo inserta sin codificar.

El navegador crea una etiqueta HTML.

Un evento ejecuta JavaScript bajo el origen de la aplicación.

OWASP A03:2021 · Injection incluye XSS (CWE-79).

02 / MITIGACIÓN + COMPROBACIÓN CSP

Codificar la salida y añadir CSP

En :3001/xss, la entrada se muestra como texto.

Escape contextual: < se representa como &lt;.

CSP es una defensa adicional.

En /csp-prueba: comparar alertas y abrir F12 → Console.

mitigado/app.js · salida y directivas clave

function mostrarComentario(texto) {
  return escaparHTML(texto);
}

Content-Security-Policy:
  default-src 'none';
  script-src 'none';
  style-src 'self';
  object-src 'none';
  base-uri 'none'
La app no necesita scripts. CSP no sustituye el escape ni la sanitización contextual.

03 / FUNDAMENTO · A10:2021

SSRF: el servidor hace la petición

El usuario controla un destino consultado por el backend.

Se aprovecha la conectividad del servidor.

Impacto: acceso a servicios internos o metadatos.

La demo utiliza un secreto totalmente ficticio.

¿QUIÉN SE CONECTA?

Usuario → URL elegida

Aplicación → petición HTTP al destino

Servicio interno → respuesta a la aplicación

Aplicación → datos devueltos al usuario

OWASP A10:2021 · En SSRF actúa el servidor; en XSS actúa el navegador.

03 / MITIGACIÓN INMEDIATA

Destinos fijos, sin redirecciones

Allowlist exacta: esquema, IP, puerto y ruta.

IP literal: sin resolución DNS en esta demo.

Catálogo permitido → HTTP 200.

Servicio interno → HTTP 403.

Complemento real: restricciones de salida de red.

mitigado/app.js · consultarRecurso (fragmento)

if (!destinosPermitidos.has(url)) {
  const error = new Error(
    'Destino bloqueado'
  );
  error.status = 403;
  throw error;
}
const destinoFijo =
  destinosPermitidos.get(url);
return descargar(destinoFijo, {
  redirect: 'error'
});
Con dominios: controlar IP efectiva, IPv4/IPv6, DNS rebinding y rangos reservados.

CONCLUSIONES

Tres límites de confianza

Acceso roto: usuario → objeto ajeno.

XSS: dato → código del navegador.

SSRF: entrada → conexión del servidor.

CONTROL QUE CORRIGE CADA FALLA

Autorización por objeto en backend.

Salida codificada según el contexto + CSP.

Destinos permitidos y redirecciones bloqueadas.

Verificar siempre: ataque rechazado y uso legítimo conservado.

No confiar en la entrada del cliente para decidir permisos, código o destinos.
